# BitVoid Server API v1 contract

Status: proposed implementation contract shared by the Android app and the headless application Server.

## Architecture boundary

- The Android application is the only user-facing client.
- The Gateway supplies local Wi-Fi, gateway health, and (where supported) discovery. It does not own application accounts, messages, channels, classes, or application persistence.
- The application Server is the authority for pairing, device authentication, application data, synchronization, and real-time events.
- The Android app talks directly to the Server over the selected local Wi-Fi network. It must not send chat or application requests to the Gateway.
- Cloud services are optional and must not be required for local-network operation.

## Network defaults and discovery

- Default Server API port: TCP 8787.
- HTTP base URL: `http://<server-ip>:8787`.
- WebSocket URL: `ws://<server-ip>:8787/api/v1/events`.
- Preferred DNS-SD service: `_bitvoid-server._tcp.local.`.
- Preferred hostname: `bitvoid-server.local`.
- The app must use the resolved Server address on the Android Wi-Fi `Network`; it must not silently route local traffic over cellular.
- The Gateway address (currently 192.168.4.1) is not the Server address. The Server is a separate device connected to the same local network.
- Discovery is advisory. The app must verify `GET /api/v1/server/info` and the returned server identity before trusting a discovered endpoint.

## HTTP conventions

- All paths are versioned under `/api/v1`.
- JSON request and response bodies use UTF-8 and `application/json`.
- Authenticated routes require `Authorization: Bearer <device-token>`.
- The Server must never accept the Gateway's private trust secret as an app-user credential.
- Mutating requests should accept an `Idempotency-Key` so the app can safely retry after a dropped connection.
- Timestamps are ISO-8601 UTC strings.
- IDs are opaque strings generated by the Server.
- Pagination uses opaque cursors, not client-generated offsets.

## Common response envelope

Success:
```json
{
  "data": {},
  "meta": {
    "requestId": "req_opaque",
    "serverTime": "2026-11-26T17:00:00Z"
  }
}
```

Error:
```json
{
  "error": {
    "code": "validation_error",
    "message": "A human-readable explanation",
    "details": {}
  },
  "meta": {
    "requestId": "req_opaque"
  }
}
```

Use appropriate HTTP status codes: 400 validation, 401 missing/invalid token, 403 forbidden, 404 missing resource, 409 conflict, 413 payload too large, 429 rate limit, and 5xx server failure.

## Endpoint contract

### Health and identity

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/v1/health` | No | Liveness/readiness and API version |
| GET | `/api/v1/server/info` | No | Stable server ID, display name, protocol/API versions and capabilities |

The Server identity response must include `serverId`, `displayName`, `apiVersion`, `eventProtocolVersion`, `capabilities`, and `links`. Do not identify the Gateway as the Server.

### Pairing and device authentication

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/api/v1/pairing/requests` | No | Create a short-lived pairing request for this app installation |
| GET | `/api/v1/pairing/requests/{requestId}` | Pairing secret | Poll pairing status |
| POST | `/api/v1/pairing/requests/{requestId}/approve` | Admin | Approve/reject from an authorized admin client |
| POST | `/api/v1/auth/token` | Pairing proof | Exchange approved pairing proof for a device token |
| POST | `/api/v1/auth/revoke` | Device | Revoke the current device token |
| GET | `/api/v1/me` | Device | Return current account and device identity |

Pairing requests must expire, be rate-limited, and be bound to a device installation. Device tokens must be revocable and stored securely by Android. Do not put long-lived tokens in WebSocket query parameters.

### Conversations and messages

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/v1/conversations` | Device | List conversations |
| POST | `/api/v1/conversations` | Device | Create a direct/group conversation |
| GET | `/api/v1/conversations/{id}/messages` | Device | Fetch message history using cursor pagination |
| POST | `/api/v1/conversations/{id}/messages` | Device | Send a message |
| POST | `/api/v1/messages/{id}/receipts` | Device | Update delivered/read receipt |

Message payloads must contain a client-generated `clientMessageId`, message type, content or attachment metadata, and optional reply reference. The Server assigns the canonical `messageId`, persists the message, and acknowledges it before broadcasting `message.created`. Enforce membership and authorization on every request.

### Channels and Live Classes

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET/POST | `/api/v1/channels` | Device | List/create channels |
| GET/PATCH/DELETE | `/api/v1/channels/{id}` | Device | Read/update/delete where permitted |
| GET | `/api/v1/channels/{id}/messages` | Device | Read channel history |
| POST | `/api/v1/channels/{id}/messages` | Device | Publish a channel message |
| GET/POST | `/api/v1/live-classes` | Device | List/create Live Classes |
| GET | `/api/v1/live-classes/{id}` | Device | Read class details |
| POST | `/api/v1/live-classes/{id}/join` | Device | Join a class |
| POST | `/api/v1/live-classes/{id}/leave` | Device | Leave a class |

Live audio/media transport may use a separate negotiated media channel. The REST API controls class metadata, membership, and signaling; it must not pretend that JSON WebSocket events alone carry real-time audio.

### Offline synchronization

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/v1/sync?cursor={cursor}` | Device | Return ordered changes since the opaque cursor |

The sync response includes ordered changes, a new cursor, and server time. The app keeps an encrypted local outbox for unsent operations, retries with the same `Idempotency-Key`/client message ID, and removes an item only after a durable Server acknowledgement. The Server must make repeated submissions idempotent.

## WebSocket event protocol

Connect to `/api/v1/events` with the same bearer token in the HTTP Authorization header. The Server authenticates the handshake and authorizes every subscription.

Client frames:
```json
{ "type": "subscribe", "conversationIds": ["conv_1"], "channelIds": ["channel_1"], "liveClassIds": ["class_1"] }
```
```json
{ "type": "ping", "id": "ping_1" }
```

Server event envelope:
```json
{
  "eventId": "evt_opaque",
  "type": "message.created",
  "occurredAt": "2026-11-26T17:00:00Z",
  "data": {
    "messageId": "msg_opaque",
    "conversationId": "conv_opaque",
    "senderId": "device_or_user_id",
    "clientMessageId": "client_generated_id",
    "content": { "type": "text", "text": "Hello" }
  }
}
```

Initial event types: `message.created`, `message.updated`, `message.deleted`, `receipt.updated`, `typing.started`, `typing.stopped`, `presence.changed`, `channel.created`, `channel.updated`, `live_class.started`, `live_class.ended`, `live_class.participant_joined`, `live_class.participant_left`, and `sync.available`.

Events are hints for immediate UI updates, not a replacement for durable sync. Events carry unique IDs; after reconnect the app calls the sync endpoint with its last durable cursor to recover missed changes. The Server should send ping/pong heartbeats and close expired/revoked sessions.

## Android client requirements

- Bind all local HTTP and WebSocket sockets to the Android Wi-Fi `Network` selected for BitVoid.
- Resolve and verify the Server separately from the Gateway.
- Keep the device token in Android secure storage; never log it.
- Expose connection state (disconnected, discovering, connecting, authenticated, reconnecting, error).
- Use bounded exponential reconnect with jitter for WebSocket.
- Queue outgoing messages locally and retry idempotently.
- Apply incoming events to the local database, then advance the sync cursor only after durable persistence.
- On reconnect, run sync before declaring the client fully synchronized.
- Do not use the Gateway's `/api/v1/internal/status` trust header for app authentication.

## Gateway compatibility boundary

The current ESP Gateway remains Wi-Fi AP + health + discovery only. It must not implement application routes, WebSocket chat, pairing, channel persistence, or Live Class state. A future Gateway discovery enhancement may advertise the Server's address, but the app still connects directly to the Server.

## Implementation order

1. Complete physical Gateway Wi-Fi, health, station-count and stability tests.
2. Implement the headless Server against this contract (Fastify, persistent database, REST and WebSocket).
3. Add Server discovery/connection and this API client to the Android app.
4. Integrate pairing, messaging, channels, Live Classes and offline sync feature-by-feature.
5. Add integration tests with the Gateway and Server on the same isolated Wi-Fi network.

No GitHub Actions are required for this work.
